# Design 1.6: Client data isolation for AEO data (options)

Status: options for the dev team. The approach is Brian Watson's and Brian Magazu's call; PM recommends Option C. Other work does not wait on this decision. Docs only; no migrations.
Evidence: read-only catalog queries on the main project (qftczrlksczfimnzfiov), 2026-11-17; ifai-dashboard `lib/supabase/canvas-client.ts`, `lib/command/session.ts`.
Hard rule (CLAUDE.md): no slice that exposes AEO data to client logins ships without org-scoped RLS and tests proving isolation.

## 1. Current state (facts)

### 1.1 URGENT: client data is readable with the public anon key
The anon key (publishable key) is public by design: it ships in browser bundles of the dashboard (`NEXT_PUBLIC_SUPABASE_ANON_KEY` in `canvas-client.ts`) and the portal. Anyone holding it can read:

| Schema | Relations readable by `anon` | How |
| --- | --- | --- |
| ledlenser | 33 | All are views without `security_invoker=true`, so they run as the owner and bypass RLS |
| public | 63 (37 owner-rights views such as `canvas_retail_listings`, `canvas_ai_citations`, `canvas_listing_sales_loss_v2`; 26 tables) | Owner-rights views bypass RLS; `canvas_score_snapshots` has an anon `using (true)` policy |
| sandbox | 22 (18 tables with `*_read_all` policies `using (true)` for anon and authenticated; 4 owner-rights views) | Explicit read-all policies |
| command | 6 tables granted to anon | No anon policies found, so RLS should block rows; verify |

Signed-in users: every `command` FMIC table has an `authenticated` SELECT policy `using (true)`. Any login (any org) can read all FMIC data.

Impact: FMIC (Fender) and Ledlenser listing, pricing, AI answer and citation data is readable by anyone with the anon key. This breaks client data isolation today, before any portal work ships.
Owner: per ifai-dashboard AGENTS.md, permission changes wait for Brian Watson. Recommended immediate step (Step 0 below) is independent of the portal plan.
Dev team position (2026-11-17): aware; the data is public today by design of the current dashboard; it will move behind secure login before proprietary data is used.

### 1.1a Write functions callable with the anon key (do first)
These five functions are `SECURITY DEFINER` in `public` and executable by `anon` and `authenticated`. They change data, so anyone with the public key can write, not only read:

| Function | Arguments |
| --- | --- |
| `ai_prompt_save` | p_prompt_key, p_prompt_text, p_category |
| `ai_prompt_set_active` | p_prompt_key, p_active |
| `mark_issue_done` | p_client_key, p_check_key, p_entity_key, p_name, p_note, p_entity_label |
| `set_aside_issue` | p_client_key, p_check_key, p_entity_key, p_reason_code, p_name, p_note, p_entity_label |
| `reopen_set_aside` | p_id, p_name, p_note |

Recommended early fix: `revoke execute ... from anon` (and from `public`) on all five, keep `authenticated` only where the dashboard calls them after sign-in, and add a membership check inside each function in Step 1.

### 1.2 Data model facts
- Per-client schemas: `command` (FMIC, `fmic_*` tables) and `ledlenser`. No organization column. Client identity is the schema itself.
- `sandbox` is the new normalized model keyed by `client_id`. `sandbox.client` already has `organization_id uuid` (PLAN 1.1 column exists; population and FK not verified).
- Two org models: portal uses `public.organizations` / `public.organization_memberships`; the dashboard signs users in against `command.organizations`, `command.user_profiles`, `command.organization_memberships` (with `is_platform_org`). PLAN 1.2 ("retire duplicates") must first move the dashboard to `public.*`.

## 2. Options

### Option A: Converge on the org-scoped `sandbox` model
All client data lives in `sandbox`, keyed by `client_id`; `sandbox.client.organization_id` links to `public.organizations`. One helper, `private.can_read_client(client_id text)`, checks the caller's active membership in that org (or `platform_admin`). Every client table gets `using (private.can_read_client(client_id))`. Views are `security_invoker=true`.
- Pros: one model for 100 clients (company 18-month goal); new clients need rows, not schemas; RLS is uniform and testable.
- Cons: `command` and `ledlenser` pipelines (for Ryan) and dashboard reads must move to `sandbox`; largest effort; FMIC history tables are large (165K and 152K rows).

### Option B: Keep per-client schemas; expose only through org-checked views or functions
Add `private.client_schema_org (schema_name text primary key, organization_id uuid)`. Revoke direct table and view access from `anon` and `authenticated` in client schemas. Expose data only through `security_invoker=true` views over tables whose RLS checks `private.can_read_schema('ledlenser')`, or through security definer functions that assert membership first.
- Pros: fastest; pipelines unchanged.
- Cons: a schema per client does not scale to 100; every new view must remember the check; the 70 existing owner-rights views each need rework; more surface for mistakes.

### Option C (recommended): Lock down now, converge to A
- Step 0 (urgent, separate from portal phases): first revoke `anon` EXECUTE on the five write functions (1.1a); then revoke `anon` SELECT on all client data in `command`, `ledlenser`, `sandbox` and the public `canvas_*` views; set `security_invoker=true` on views; replace `using (true)` policies with membership checks via the Option B mapping table. The dashboard must sign users in before reading (it already has auth through `command.*`).
- Step 1 (PLAN 1.6): Option B mapping plus catalog-driven isolation tests, so client logins can be enabled safely.
- Step 2 (after MVP or as pipelines are touched): move `command` and `ledlenser` into `sandbox` (Option A); retire per-client schemas; then 1.2.
- Pros: closes the exposure in days; keeps the path to one model. Cons: two rounds of view work.

## 2a. Approved rule (user, 2026-11-17)
Module data access always comes from the signed-in user's account membership (`public.organizations`), never from a client or account ID passed in a link, URL or request. Any helper that takes an account or client id must check the caller belongs to it.

## 3. Isolation test plan (all options)
Fixtures on a local stack: org A (client), org B (client), IntoFocus platform org; users: A admin, A member, B admin, platform_admin, anon.
1. For each client relation: A users see only A rows; B users see only B rows; anon sees nothing; platform_admin sees all.
2. Catalog guard test (stops regressions): fail if any relation in a client schema, or any public view reading client schemas, is selectable by `anon`; fail if any such view lacks `security_invoker=true`; fail if any client-table policy uses a literal `true`.
3. Function guard: every security definer function returning client data calls the membership helper (checked by test calls as B user against A data).
4. Run in CI on every PR that touches migrations.
