# Builder brief: 1.6 Client data isolation (lock down AEO data)

You are a builder session for the IntoFocus AI client portal. The PM session wrote this brief. Work only on what is below.

## Goal (user approved 2026-11-18: build Option C now; Watson and Brian review and decide by approving the PR)
Today the dashboard's client data (FMIC in `command`, Ledlenser in `ledlenser`, the normalized `sandbox` model and the public `canvas_*` views) is readable with the public anon key, every signed-in user can read all FMIC data, and five write functions are callable by anon. ## Essentials of the design
- Step 0a: `revoke execute` from `anon` and `public` on `public.ai_prompt_save`, `ai_prompt_set_active`, `mark_issue_done`, `set_aside_issue`, `reopen_set_aside`. Keep `authenticated`. Check in the dashboard code that these are only called after sign-in; list any call that is not.
- Step 0b: revoke `anon` SELECT on every relation in `command`, `ledlenser`, `sandbox` and every public view that reads them (`canvas_*` and others found in the snapshot). Set `security_invoker = true` on those views. Replace every `using (true)` policy on client data with a membership check.
- Step 1: mapping and helpers.
  - `private.client_schema_org (schema_name text primary key, organization_id uuid not null references public.organizations)` for per-client schemas (`command` = FMIC account, `ledlenser` = Ledlenser account). Rows are inserted by Watson at apply time (the account ids are not known to you); the migration creates the table only and documents the insert.
  - `sandbox.client.organization_id` already exists: add the foreign key to `public.organizations` (not valid first, validate later if existing rows lack it; document).
  - `private.can_read_schema(schema_name text)` and `private.can_read_client(client_id)` (use the real key type of `sandbox.client`): true when the caller is an active member of the mapped account, or staff (`private.is_staff()`); staff reads are allowed only where the account is entitled, matching the portal rule (staff read only and logged; reuse `private.module_access` if it fits, else document the gap).
  - Policies on every client table use these helpers. Security definer functions that return client data check the helper first.
  - Access always comes from the signed-in user's membership, never from an id passed in a request (approved rule).
- Platform org: the dashboard's IntoFocus staff use `command.organizations.is_platform_org`; the portal uses `private.is_staff()`. Use `private.is_staff()`; list any staff user who would lose access so Watson can grant the portal staff role first.
- Do not move data between schemas (Option A is a later step).

## Tests
- Isolation: org A, org B, staff, anon. For every client relation: A sees only A, B only B, anon nothing, staff only entitled accounts.
- Catalog guard tests (fail the build): any client relation or view over client data selectable by anon; any such view without `security_invoker`; any client policy with literal `true`; any security definer function over client data without the helper call.
- Write functions: anon refused.
- Dashboard impact: list every place the dashboard reads with the anon key before sign-in (these break after Step 0b). Do not rewrite the app here; a separate builder moves the dashboard to signed-in reads (issue "Open the dashboard from the portal"). Coordinate through the PM.
