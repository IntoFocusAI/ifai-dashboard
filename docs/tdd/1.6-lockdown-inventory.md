## Not changed, for Brian Watson

After the migrations, anon still holds INSERT, UPDATE or DELETE grants (Supabase default privileges on `public`) on 20 objects that are not dashboard client data. Row level security already blocks anon on each: the portal tables have membership policies, and brand_tokens, components, variants and votes have RLS with no policies. Revoking these is a separate permission change:

organizations, organization_memberships, profiles, people, departments, modules, role_assignments, role_responsibilities, role_seats, work_items, work_dependencies, work_milestones, work_source_links, brand_tokens, components, variants, votes; sequences module_key_seq and work_item_key_seq. ## Apply-time notes (PM review of PR 251)

1. **Roles come from the command sign-in tables only** (rework, 2026-11-23). Staff = active `intofocus_admin` on the platform org (`command.is_intofocus_admin()`), who read every client; Org Leads (`org_admin`) and Org Users (`org_viewer`) read the client mapped to their org in `command.client_organizations`. Apply `20261123120000` (mapping) and `20261123120100` (Lead limits) first. Nothing in the portal's `public.*` identity tables is read. `public.audit_log` is a portal table and keeps its own policy; it only loses anon. Before applying, list who will read what:
   `select u.email, o.slug, m.role, m.status from command.organization_memberships m join command.organizations o on o.id = m.organization_id join auth.users u on u.id = m.user_id order by 2, 1;`
2. `grant usage on schema private to authenticated` (already granted on hosted) is safe only while `private` stays out of the API's exposed schemas: Postgres gives PUBLIC EXECUTE on new functions by default. The portal launch sweep (5.1) checks this, and `catalog_guard.test.sql` fails if a `private` function outside the helper list is callable by signed-in users.
3. The default-privilege statements use `for role postgres`, the role that owns the client schemas and creates their objects on hosted. Objects created by another role (for example `supabase_admin`) are not covered by them; the catalog guard catches any such object granted to anon.
4. `private.is_backend_caller()` treats any direct database session as a backend caller, including `cursor_map_writer` and `cursor_schema_reader`, so those sessions read the materialized view readers in full. This is intended for pipelines; it matches how these roles see tables (`cursor_map_writer` already has BYPASSRLS).
